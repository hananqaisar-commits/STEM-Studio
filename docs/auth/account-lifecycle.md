# Account persistence and authentication lifecycle

## Findings

- The application uses its configured SQL database and has no in-memory fallback or account-cleanup job. Registration commits the user and preferences in one transaction. Regular learner email verification is disabled by default; those accounts are immediately usable without an email provider. Set `EMAIL_VERIFICATION_REQUIRED=true` only if inbox verification is intentionally enabled. Owner sign-in always retains its separate verified-account and MFA requirements. Production startup now rejects SQLite and local database hosts so a redeploy cannot quietly create an empty, ephemeral account store. The backend must use the same managed PostgreSQL database where the owner was provisioned.
- The account table has unique email and username constraints. Signup and Google sign-in normalize email addresses to lowercase before insertion. Registration now maps a concurrent uniqueness conflict to HTTP 409 instead of returning an unhandled database error.
- JWT/session expiration does not delete a user row. The configured defaults are a 15-minute access token, a 7-day refresh session, and an optional 30-day remembered session. The sign-in page defaults “Remember me” on. Refresh credentials are hashed in `user_sessions`; rotated tokens are single-use and replay revokes active sessions. Signing out means the session needs renewal; the account remains stored until the user explicitly confirms deletion.
- There was a client-side session-loss path: all simultaneous 401 responses could independently rotate the same refresh token, and the backend's replay protection then revoked sessions. The frontend now shares refresh work across concurrent requests and uses the browser Web Locks API across tabs where available. It preserves stored credentials on network, throttling, and server failures, and retries one transient profile-load failure.
- Before this change, the profile bootstrap cleared tokens for every error, including temporary network/server failures. These paths can make a persisted account look signed out, but without deployment logs the reported 15–20-minute event cannot be conclusively tied to one of them.
- Platform `registered_learners` is the total account-row count and `active_learners` counts accounts with `is_active=true`; neither is a live-presence metric. Signup, Google account creation, account deletion, and owner suspension/restoration invalidate the short-lived Redis cache. The public landing page displays `active_learners` and refreshes it every minute; it hides the count if the API is unavailable rather than displaying a guess.

## Account deletion

The authenticated user can request deletion from Settings → Account. The request requires the literal confirmation `DELETE` and an access token issued by a sign-in within the configured 10-minute window. The server derives the account identity from the bearer token and commits the deletion transaction before returning success. SQLAlchemy cascades remove the user's sessions, verification/reset tokens, learning progress, quiz attempts, streak, saved sessions, login-attempt records, and role associations. Shared reviews are not user-owned and are not deleted. The frontend clears both token stores after a successful response.

## Email configuration not completed

The shared branded email sender supports password reset, billing notices, optional owner announcement email, and optional learner verification. It defaults to Resend's HTTPS API; SMTP remains available by explicitly selecting it on a host that permits SMTP egress. Provider credentials and sender-domain DNS are not configured here, and no real email was sent. By default, learner signup and sign-in do not wait for email delivery; the backend still validates email syntax and enforces unique addresses. Existing unverified learner accounts become usable after a successful password sign-in. To require inbox verification, set `EMAIL_VERIFICATION_REQUIRED=true` and configure a working email provider. Owner sign-in continues to require a verified account independently of this setting. Provider acceptance does not guarantee inbox delivery.

For the default Resend provider, configure `EMAIL_PROVIDER=resend`, `RESEND_API_KEY`, `EMAILS_FROM_EMAIL`, `EMAILS_FROM_NAME`, optional `EMAILS_REPLY_TO`, and an HTTPS `FRONTEND_URL` on the backend host. Verify a domain you own in Resend and publish exactly the DNS records it gives you. Keep the API key out of the frontend and source control. See [STEM Studio email delivery setup](../email-delivery-setup.md). Password-reset expiry is configured with `PASSWORD_RESET_TOKEN_EXPIRE_MINUTES` (20-minute default); verification token expiry applies only when verification is enabled.

## Persistence and deployment

Use the same durable managed PostgreSQL/MySQL service for every API instance. Do not point replicas at separate local SQLite files. For container recreation, retain the external database or its managed persistent volume; Redis is for shared rate limits/cache and is not the account store. Production startup now fails instead of serving against SQLite or an unavailable database. The app's startup `create_all` creates missing `support_tickets`, `user_preferences`, `announcements`, `announcement_recipients`, and `announcement_reads` tables; production still needs a backup and a restart/redeploy before those routes are used. No existing table columns are altered by these additions.

## Support and review ownership

Signed-in learners can create support tickets and read their own request history. Listing/responding to tickets, moderating reviews, and broadcasting announcements require an owner account created through the restricted server-side provisioning command plus a valid TOTP-authenticated owner session. `SUPPORT_OWNER_EMAILS` is deprecated and no longer grants access. See [Owner Control Center setup](../owner-control-center.md). Production owner credentials and the MFA encryption key must be provisioned by the deployment operator; no default owner account exists.

The provisioned owner role plus a verified owner session grants access to the dashboard broadcast panel. Publishing stores a single announcement plus a database snapshot of its active recipients. Later-created users are excluded from old broadcasts. Each signed-in recipient has an independent read receipt; the navbar badge gets its unread count from the API and polls every 30 seconds (and on tab focus). Announcements always have in-app delivery; the owner can also choose optional email delivery using the shared sender. Promotions/product updates go only to opted-in recipients. No real email was sent during this repository work.
